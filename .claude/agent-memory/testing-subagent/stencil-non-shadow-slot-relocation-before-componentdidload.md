description: Non-shadow Stencil components physically relocate light-DOM slotted children before componentDidLoad fires, breaking any direct-childNodes slot-content check (e.g. hasSlotContent(this.el)) run from that lifecycle hook or later (slotchange handlers included).
metadata:
  type: project

Confirmed via `bds-button` (`@Component({ tag: 'bds-button', formAssociated: true })` — no `shadow: true`, so it runs in Stencil's non-shadow/light-DOM mode). Stencil's non-shadow slot polyfill (`relocateNodes` in `@stencil/core/internal/testing`) physically moves original light-DOM children out of being direct children of the host element and into the rendered `<slot>` placeholder's position, as part of the first vdom patch — which completes *before* `componentDidLoad` runs.

Repro: `newSpecPage({ components: [BdsButton], html: '<bds-button name="x">Delete item</bds-button>' })`, then inspect `page.root.outerHTML` — the text "Delete item" ends up nested inside `<span class="bds-button__content-text">`, and `page.root.childNodes` only contains a comment marker, a whitespace text node, and the `<button>` element. It is no longer a direct child of the host.

**Consequence:** any diagnostic/logic written as `hasSlotContent(this.el)` (checks `el.childNodes` directly, non-recursively — see `packages/boreal-web-components/src/utils/dom/elements.ts`) and called from `componentDidLoad` will **always** evaluate default-slot content as absent, regardless of actual usage. This produced a real false-positive bug in `bds-button`'s `checkAccessibleName()` (added for ticket AI-001): a plain `<bds-button>Delete item</bds-button>` with no `label` incorrectly fires the "no accessible name found" `console.warn`, even though it has visible slotted text.

Named-slot content (e.g. `[slot="icon"]`) is unaffected because it's typically detected via `el.querySelector('[slot="icon"]')`, which searches the whole subtree recursively and finds the element regardless of which depth it was relocated to — the DOM attribute survives relocation, only the parent changes.

**Fix applied (AI-003, `bds-button`):** `componentWillLoad` now sets `hasTextContent = hasSlotContent(this.el)` (pre-relocation, correct), and `componentDidLoad` does an **upgrade-only merge** — `this.hasTextContent = this.hasTextContent || hasSlotContent(this.el)` — never a blind reassignment, so a correct `true` from `componentWillLoad` can't be clobbered by a stale `false` read post-relocation.

**Sibling bug found and fixed in the same session:** the component also had a `handleTextSlotChange` bound to the `<slot>`'s `onSlotchange`, meant to re-detect content added/removed *after* initial load — it also called `hasSlotContent(this.el)`, which is host-childNodes-only. Since Stencil suppresses `slotchange` during the initial render (`!isInitialLoad` guard) but fires it for real on every subsequent relocation, and by the time any post-load `slotchange` fires the content has *already* been relocated out of the host's direct children, this handler could **never** correctly detect post-load content changes in either direction — it always read `false`, whether or not content was actually present. Confirmed by direct repro: appending text and calling the handler set `hasTextContent = true` for one tick, then Stencil's own state-triggered re-render relocated the new node and re-dispatched `slotchange`, and the handler's blind reassignment flipped it back to `false`.

**Correct fix for post-load/slotchange-time checks:** check the *rendered wrapper's* content, not the host — `this.el.querySelector('.bds-button__content-text')?.textContent?.trim() !== ''`. `componentWillLoad`'s `hasSlotContent(this.el)` check remains correct only because it runs pre-relocation; any check that runs after the component's first render (slotchange handlers, later lifecycle hooks, imperative calls) must inspect the already-rendered DOM location instead.

**Testing implication:** don't assume `hasSlotContent`-style host-childNodes checks reflect current DOM state anywhere except `componentWillLoad`. Simulating a `slotchange`-driven update in `newSpecPage` reliably: mutate the *rendered wrapper's* childNodes directly (e.g. `root.querySelector('.bds-button__content-text').appendChild(...)`/`.removeChild(...)`), then invoke the private handler via `page.rootInstance` cast to an internals type — a real `slotchange` round-trip via `root.appendChild()` on the host is not reproducible in this mock-doc for content added to an originally-empty default slot (the patched `appendChild` falls back to a plain host-level append instead of finding/relocating through a slot marker, since none was ever created for an empty slot).
