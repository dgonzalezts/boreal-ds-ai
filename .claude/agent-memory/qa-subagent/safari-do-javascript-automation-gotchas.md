## Safari real-browser QA via AppleScript `do JavaScript` — two hard-won gotchas (EOA-17138 Task 20 Safari re-verification, 2026-09-03)

Context: Playwright's bundled WebKit could not reproduce the Task 19r Safari/WebKit Apply-button bug (documented elsewhere), so real Safari.app automation was required. `playwright-cli --browser=webkit` is NOT a substitute for real Safari.app for this bug class. Neither System Events GUI scripting (`osascript -e 'tell application "System Events" to click ...'`) nor `safaridriver --enable` (WebDriver) are usable without an interactive user granting Accessibility permission / entering an admin password — both are one-time GUI/password prompts this agent cannot satisfy non-interactively. The viable fallback is Safari's AppleScript `do JavaScript "..." in document` command (requires `defaults write com.apple.Safari AllowJavaScriptFromAppleEvents -bool true`, then fully quit+relaunch Safari once for it to take effect — a one-time, non-interactive `defaults write`, not a GUI toggle).

**Gotcha 1 — synthetic click events must set `detail: 1`.** `bds-button`'s internal `handleClick` (`bds-button.tsx`) has `if (event.detail === 0) return;` — a legitimate anti-spoofing/real-click guard. Any synthetic `new MouseEvent('click', {...})` dispatched via `do JavaScript` defaults `detail` to `0` and silently no-ops every `bds-button` click (Apply/Cancel/Clean footer buttons, calendar nav arrows, any button-wrapped action) with ZERO error — looks exactly like "nothing happened," easily misdiagnosed as a real regression. Fix: always pass `detail: 1` explicitly in the `MouseEventInit`/`PointerEventInit` for any dispatched pointerdown/mousedown/click sequence. Plain native `<td onClick>` handlers (e.g. calendar day cells) have no such guard and work fine with `detail: 0`/omitted — the guard is specific to `bds-button`.

**Gotcha 2 — the target Safari tab/window MUST be frontmost (not occluded/backgrounded) or Stencil's re-renders silently never paint.** Stencil's own `@State`/`@Prop` writes DO update the component's internal instance fields correctly even in a backgrounded tab (confirmed via `element.__stencil__getHostRef().l` direct inspection) — the state layer itself is unaffected. But Stencil's actual re-render scheduling (`Ke`/`scheduleUpdate` in the compiled runtime) is gated behind `requestAnimationFrame`, and Safari (like all modern browsers) throttles/suspends `rAF` callbacks for tabs that are not the frontmost, visible, composited tab — including tabs created via `do JavaScript`'s own `make new document`, which are NOT automatically frontmost/focused. Symptom: click events fire correctly, custom events (`bdsDayClick`/`bdsMonthNavigate`/etc.) bubble correctly, internal `@State` fields update correctly (all independently verifiable), but the DOM never visibly updates — loofirs. Cheapest diagnostic: `requestAnimationFrame(() => window.__rafFired = true)` then poll `window.__rafFired` after a delay; `false` means the tab isn't really frontmost regardless of what `do JavaScript`'s target-document resolution reports. Fix: before every interaction batch, explicitly bring the target window to the front and set it as the current tab via AppleScript (`tell application "Safari" to activate` + `set index of window w to 1` + `set current tab of window w to targetTab`), not just target the right `document` object for script execution — script-targeting and OS-level window-frontmost-ness are two independent things in Safari's AppleScript model, and only the latter unblocks rAF.

Combined effect if you miss #2: it looks exactly like every `@Listen`-decorated internal handler is broken while manually-`addEventListener`'d listeners on the identical event/target somehow "work" — because your own ad-hoc listener runs synchronously as part of event dispatch (unaffected by rAF), while Stencil's actual visual re-render (the only way to observe the internal state change from outside) never happens. This is a purely observational artifact of the automation harness, not a real product bug — do not report a false regression before checking rAF firing.

Multi-document AppleScript gotcha: `document 1` in `tell application "Safari"` refers to the frontmost window's document by z-order, NOT the most-recently-created one via `make new document`. After creating a new tab, resolve the correct document by matching `URL of d starts with targetURL` across `documents`, not by index.
