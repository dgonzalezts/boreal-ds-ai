description: Conditionally toggling a light-DOM child's named-slot region (e.g. bds-popover's header/footer prop) does NOT hide the parent's slotted content for that name — the parent must independently gate its own JSX or the un-relocated content still paints
metadata:
  type: project
---

When a light-DOM (`shadow: false`) Stencil child component conditionally renders a named `<slot name="x">` target (e.g. `bds-popover`'s `{this.footer && (<div class="popover-footer"><slot name="footer-button"></slot></div>)}`), and the parent unconditionally declares `<div slot="footer-button">...</div>` as JSX children regardless of the child's prop, Stencil's non-shadow slot-relocation polyfill only moves/positions content when a matching `<slot>` exists in the *current* render output. When the child's vdom omits that `<slot>` (prop is `false`), the parent's already-real light-DOM nodes with that `slot="..."` attribute are simply never relocated/hidden — they remain as orphaned children of the child element and can still paint (unstyled, in raw DOM order), visually leaking content the boolean prop was supposed to suppress entirely.

**Why:** Found in `bds-date-picker`'s Task 15c (`calendarType='default'` should hide `bds-popover`'s header/footer chrome entirely). Setting `header={showChrome} footer={showChrome} closable={showChrome}` on `<bds-popover>` was necessary but NOT sufficient — `bds-date-picker`'s own render() still unconditionally emitted `<i slot="header-icon">`, `<span slot="header-title">`, and `renderFooter()`'s `<div slot="footer-button">` buttons regardless of `showChrome`. Result: in `calendarType='default'`, the popover opened with no header (as expected) but the Clear/Cancel/Apply footer buttons still visually rendered (in the wrong DOM position, above the calendar) even though `popover.footer === false` and `.popover-footer` never existed in the DOM. Confirmed via direct `popover.header`/`popover.footer`/`querySelector('.popover-footer')` JS inspection in a live browser — the compiled bundle's boolean logic was 100% correct; the bug was structural (orphaned un-gated slotted JSX), not a stale-build or logic bug. Unit tests (`newSpecPage`) never caught this because jsdom-based specs assert on JS properties/classes, not actual visual paint order of un-relocated content.

**How to apply:** Any time a parent conditionally toggles a light-DOM child's boolean prop that gates a named `<slot>` region (`header`, `footer`, `closable`, or any custom equivalent), audit every piece of the parent's own JSX that targets that slot name via `slot="..."` and gate it with the *same* condition — never assume the child's own prop-driven `{cond && <slot/>}` is enough to make already-declared parent content disappear. Verify visually in a real browser (manual QA), not just via `newSpecPage` JS-property assertions, since jsdom won't surface the orphaned-paint symptom.
