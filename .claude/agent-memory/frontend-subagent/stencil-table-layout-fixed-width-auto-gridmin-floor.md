`table-layout: fixed` + `width: 100%` on a table where every column has an explicit width, and the sum of those widths is less than the container, causes the browser to proportionally re-inflate all column widths to fill the container (no auto-width column exists to absorb the slack). Confirmed empirically with a real Chromium instance via playwright-cli — this is real, not a myth. Mixed explicit+auto column tables are NOT affected: the auto column correctly absorbs slack, other columns keep their exact width. So any fix must be conditional on "every column has an explicit width," not a blanket CSS change.

The first fix attempt — switching to `width: auto` when all columns are explicit-width — resolves the inflation bug (columns hold their initial widths) but introduces a **second**, easy-to-miss real-browser bug: when a table's `width` is `auto` (or `max-content`), `table-layout: fixed` still applies the CSS Tables **GRIDMIN** rule — the table (and each column) cannot shrink below the *min-content* width of its cells, even though the layout algorithm is nominally "fixed." Empirically confirmed: an 8-column-wide header cell with icons/label refused to shrink below ~148–244px regardless of how small the `<col>` style.width was set. This silently breaks any UI (like `bds-table`'s keyboard/pointer column resize down to a small `RESIZE_MIN_WIDTH_PX` floor) that expects a truly fixed layout with cells clipping overflow rather than resisting shrink. jsdom/newSpecPage cannot catch this — it does no real layout — so this class of bug is invisible to unit tests and only shows up in a real browser.

The GRIDMIN floor only applies when the table's own `width` is not an explicit length. Setting the table's `width` to a real length (numeric px, or a `calc()` expression built from the columns' own declared widths, e.g. `calc(60px + 180px + 200px + 120px)`) makes `table-layout: fixed` behave as truly fixed: columns shrink exactly to the specified width, ignoring content, with overflow clipped. This is why `bds-table.tsx`'s `syncNaturalTableWidth()` builds a `calc()` string from each column's live CSS width (reading the `<col>` element's own `.style.width`, imperatively kept in sync by `applyColumnWidth()`) instead of using `width: auto` or reading back `getBoundingClientRect()` — reading back rendered geometry to decide the "fixed" width is itself circular/self-reinforcing when the table started out mid-redistribution-bug.

**How to apply:** any resizable/fixed-layout HTML `<table>` implementation (Stencil, React, plain CSS) that needs a table to size exactly to its columns' declared widths (not stretch, not content-min-floor) must set the table's own `width` CSS property to an explicit length or `calc()` expression — never leave it at `auto`/`max-content`/`100%` — whenever every column has a known width.
