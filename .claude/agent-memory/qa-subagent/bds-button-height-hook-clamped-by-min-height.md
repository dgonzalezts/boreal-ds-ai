name: bds-button-height-hook-clamped-by-min-height
description: Setting --bds-button-height smaller than the size variant's floor is silently clamped by an unrelated --bds-button-min-height custom property; verified in bds-date-picker's popover-header__close override (EOA-16692)
metadata:
  type: project
---

`bds-button.scss` exposes two separate custom-property hooks that both affect rendered height: `--bds-button-height` (applied to `.bds-button` at `height: var(--bds-button-height, fit-content)`) and `--bds-button-min-height` (applied via the `bds-button-size` mixin at `min-height: var(--bds-button-min-height, #{$height})`, defaulting to the size-variant floor: 24px sm, 32px md, 44px lg).

CSS box-model rule: the used height is `max(specified height, min-height)`. A consumer that only overrides `--bds-button-height` to something smaller than the button's size-variant floor gets silently clamped back up to the floor — `--bds-button-height: 16px` on a `size="sm"` button (24px floor) renders as 24px tall, not 16px, with no console warning or visual sign beyond content looking oddly padded.

Confirmed via `getComputedStyle` in both Chromium and WebKit (identical result — genuine CSS specificity issue, not a rendering-engine quirk): `bds-date-picker.scss` sets `--bds-button-width`/`--bds-button-height: 16px` scoped to `.popover-header__close`, but only width took effect (16px); height measured 24px because `--bds-button-min-height` was never overridden alongside it.

**How to apply:** any time a component overrides `--bds-button-height` (or `--bds-button-width`, if a symmetric `--bds-button-min-width` exists — not yet checked) to a value smaller than the button's size-variant default, it must also override the matching `min-*` custom property, or verify via `getComputedStyle` that the override actually took effect — don't trust the SCSS alone. See [[playwright-and-bds-button-conventions]].

**RESOLVED and re-verified 2026-08-19**: `bds-date-picker.scss`'s `.popover-header__close` now also sets `--bds-button-min-height: 16px`. Confirmed via `getComputedStyle`/`getBoundingClientRect` in both Chromium and WebKit — host `<bds-date-picker>`'s close `<bds-button>` and its inner native `<button class="bds-button">` both measure exactly 16×16px, with `min-height: 16px` resolved. Sanity-checked no leakage: the popover footer Clear/Cancel/Apply buttons and the calendar prev/next nav buttons remain 32px tall, unaffected since the override is scoped to `.popover-header__close`.

**Follow-up 2026-08-19 (later same day)**: the 16px override block was subsequently removed entirely from `bds-date-picker.scss` (design changed to just use `bds-popover`'s own baseline close-button sizing). This re-exposed the SAME clamping bug one layer up: `bds-popover.scss`'s own `.popover-header__close .bds-button { width: var(--bds-button-width, 20px); height: var(--bds-button-height, 20px); }` never sets `--bds-button-min-height` alongside its own height default. Result: button renders **20×24px, not 20×20px** — width resolves to the intended 20px (no `--bds-button-min-width` exists to clamp it), but height gets clamped up to `bds-button.scss`'s own `sm`-variant floor default (`min-height: var(--bds-button-min-height, 24px)`), since nothing overrides it. This was previously invisible because the (now-removed) `bds-date-picker.scss` override happened to set all three custom properties including `--bds-button-min-height`. Icon centering was NOT visually broken by this (icon centers within the 24px-tall box fine, no overflow) — this is a dimensional/shape defect (non-square close button) rather than a centering regression. Any component-scoped `.bds-button` sizing override — including a design system's own baseline component styles, not just one-off consumer overrides — must set `--bds-button-min-height` together with `--bds-button-height`, or verify actual rendered dimensions, whenever the target is below or equal to the size variant's natural floor.
