EOA-17662 Task 35 (`bds-date-picker` info banner + footer range summary, TC-23 through TC-26) manual QA against the raw web-components playground (`packages/boreal-web-components/src/index.html`, scenarios `dp-banner-s1`..`s4`) — all four test cases pass, zero console errors/new warnings throughout.

**TC-23** (banner positioning across `default`/`basic`(no range)/`basic`+`range`): confirmed via `getBoundingClientRect()` comparison, not just screenshot — banner and calendar-grid share identical left/right edges in all three scenarios; in the `basic`+`range` case (presets sidebar present), the banner starts exactly where the sidebar ends (e.g. sidebar 240–384, banner+calendar 384–827), never stretching over the sidebar. DOM confirms banner is the first child of `.bds-date-picker__date-time`, itself a sibling (not parent) of `.bds-date-picker__presets` under `.bds-date-picker__container`.

**TC-24** (close button dismissal, no persistence across reopen): close button is a native `<button class="bds-banner__close-icon">` (not a `bds-button`), so a real Playwright click works and removes the banner from the DOM (`querySelector` returns null). Closing/reopening the popover (Escape then re-click trigger) re-shows the banner — dismissal is draft-scoped, not persisted, matching the picker's existing draft-revert convention.

**TC-25/TC-26 — important semantic note**: the footer range summary is **raw elapsed time** (`end instant - start instant`, floored into days/hours/minutes), not an inclusive calendar-day count. A range from Sept 1 to Sept 18 (both `00:00`) shows **"17 days"**, not "18 days" — this matches `computeRangeDuration`'s own JSDoc ("elapsed duration... `end - start`, with no calendar-day-counting adjustment") in `packages/boreal-web-components/src/components/forms/bds-date-picker/bds-date-picker/utils/value-mapping.ts`. The test plan's "18 days" example was illustrative, not tied to a specific date pair — don't flag a differing day count as a bug without first checking the actual elapsed-time math. Confirmed correct pluralization at the exact 1-day/1-hour/1-minute boundary via `Intl.PluralRules` ("1 day, 1 hour, 1 minute" — all singular), and multi-unit plural case ("17 days, 2 hours, 30 minutes"). Footer summary persists correctly across Apply → close → reopen in both `basic` (days-only) and `expanded`+`with-time` (days/hours/minutes) modes.

**Playwright-cli technique for `bds-date-picker`'s `expanded`+`with-time` range time selectors**: the four hour/minute `bds-select` dropdowns render as `role="combobox"`. Their listbox options are `bds-list-menu-item` elements — but only the currently-selected option gets `role="option"`; every other option gets `role="menuitem"` (an ARIA quirk in `bds-list-menu`, not specific to this task). Multiple identical-looking `bds-select` listboxes exist simultaneously in the DOM (one per instance on the page, most hidden) — clicking a `bds-list-menu-item[value='NN']` by attribute alone hits a strict-mode violation across N matches. Fix: after opening a specific combobox, find the one visible listbox via `document.querySelectorAll('bds-list-menu[slot=list]')` filtered to `getBoundingClientRect().width > 0`, then scope the option click to that listbox's `id`. Similarly, a generic `#<picker-id> bds-text-field input` or `bds-text-field[slot='field'] input` selector can match 5+ inputs on a picker with time selectors (the time `bds-select`s' internal inputs match too) — grab the trigger field's specific `id` via `eval` first, then click that.
