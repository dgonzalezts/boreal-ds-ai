description: In newSpecPage, a mutable @Prop write-back plus its own @Watch handler triggers 2 render() calls per interaction (not 1) even when both writes resolve to the same final value — assert stability across repeated actions, not a literal count.
metadata:
  type: project
---

When a component writes a value to a `@Prop({ mutable: true })` field from within an event handler, and that same field has a `@Watch()` handler that in turn sets a `@State` field to the (already-equal) derived value, `jest.spyOn(ComponentClass.prototype, 'render')` inside `newSpecPage` shows **2** `render()` calls per interaction, not 1 — confirmed empirically on `bds-pagination`'s `emitPageChange`/`handleItemsPerPageChange` (writes `this.currentPage` a Prop, whose `@Watch('currentPage')` sets `this.internalCurrentPage` a State, both ending at the same normalized value). This held even though both render calls observed identical final `currentPage`/`internalCurrentPage` values — Stencil's mock-doc `newSpecPage` test scheduler does not coalesce a Prop-triggered update and a State-triggered update from the same synchronous call stack into a single flush the way a real browser's `writeTask`/rAF batching does.

**Do not assert `toHaveBeenCalledTimes(1)`** for this pattern — it is reliably 2 in the test harness and asserting 1 produces a false failure that looks like a real regression. Verified via a temporary render spy wrapped with `console.log` of `this.currentPage`/`this.internalCurrentPage` at each call — both calls carried the same final values, so the extra call is a harness scheduling artifact, not evidence of stale intermediate renders or an actual infinite loop.

**How to apply:** to prove "no infinite render loop" for a mutable-prop-write-back-plus-watcher pattern in a Stencil spec, assert **stability across two separate, distinct interactions** instead of a fixed literal count — clear the spy, trigger the interaction, capture the call count, clear the spy again, trigger a second (different-valued, so it isn't a no-op-skipped call) equivalent interaction, and assert the second count equals the first. A growing count (e.g. 2 then 4 then 8) would indicate a genuine feedback loop; a stable repeated count (e.g. 2 and 2) proves termination without hardcoding the harness's specific per-interaction render multiplier. This generalizes to any Boreal DS component following the `bds-table.selectedRows`-style "write internal interaction back to a mutable Prop" convention — check for it before writing a hardcoded exact-count render assertion.
